Which version an agent reads

Every API version lives in the same repository, each as a self-contained bundle in its own top-level directory — v2/ today, v3/ beside it when it ships. Adding a version never moves an existing one. That raises the only question that matters in practice: which one does the agent actually open, and what stops it mixing two?

Recommended

Point at the repository, not at /v2

Give the agent the root llms.txt or manifest.json and let it resolve the version. When v3 ships, latest moves and every consumer follows with no edit. This is the default you want in docs, README files and rules files.

Not github.com/…/tree/main/v2 — that is GitHub's file-browser HTML, so an agent that fetches it gets page chrome, not the bundle. Use the raw.githubusercontent.com URLs above, or a clone.

Also supported

Pin deliberately

Hard-code v2/ — or clone a release tag — when you need reproducibility: a generator's golden files, a cached agent context, a support bot that must answer for the version a customer is on. Pinning is a supported first-class case. What breaks is hard-coding v2/ while meaning "whatever is current".

Each version also ships its own v2/llms.txt. Pointing an agent at that file, rather than the root one, pins it in a single step.

The real risk

Agents do not pick a version by themselves

Left unconstrained, a model will happily read v3/domains/… and v2/foundations/… in the same task, because both are plausible retrieval hits and nothing in the text says they are alternatives. The answer that comes back is a blend of two APIs and looks entirely confident.

Version isolation is something you enforce, at three points. It is not emergent behaviour.

The four steps that keep one version in context

Resolve once, at the startThe agent's first action is to read the root manifest.json and take latest — or the version the user named. Once per task, not once per lookup.
Bind it to one prefixStore the result as a single base path, e.g. BUNDLE = analytics-okf/v3. Every later read is BUNDLE + "/…". There is now one place the version lives.
Forbid the fallback"Read only from the selected version. If a document is missing there, say so — never fall back to another version directory." Without this line the agent silently substitutes.
Filter, don't hope (RAG)In a vector store, version is a hard metadata filter at query time, never a similarity outcome. Index api_version from the path and filter on it.
Why step 3 matters most. The failure is quiet. An agent asked a v3 question that cannot find v3/domains/share-and-publish/sharing/share-views.md will search, find the v2 document, and answer from it — correctly for v2, wrongly for v3, with a citation that looks legitimate. A missing document must produce "not documented in v3", never a neighbouring version's answer.

Drop this into CLAUDE.md, a Cursor rules file, or a system prompt. It is the same four steps in the wording the recipes below use.

# Zoho Analytics API — source of truth and version selection

1. RESOLVE THE VERSION FIRST, once per task.
   Read analytics-okf/manifest.json. Use `latest` unless I name a version
   explicitly (e.g. "for v2"), in which case use that entry. Tell me which
   version you resolved before you answer.

2. BIND IT. Treat the chosen entry's `path` as BUNDLE (e.g. analytics-okf/v2).
   Read BUNDLE/how-to-use-this-bundle.md first. Every other read is BUNDLE/… .

3. DO NOT MIX VERSIONS. Read nothing outside BUNDLE. If a document you need is
   not in BUNDLE, say it is not documented for that version. Never fall back to
   another version directory, and never combine facts from two of them.

4. CITE. Quote the BUNDLE-relative file path for each fact you rely on.

What the manifest gives you

The root manifest.json is the only file whose meaning changes when a version ships. Everything it points at is immutable.

{
  "latest": "v2",
  "latest_path": "v2",
  "status_vocabulary": { "beta": "…", "stable": "…", "deprecated": "…", "sunset": "…" },
  "versions": [
    { "version": "v2", "status": "stable", "path": "v2",
      "bundle_version": "1.0.0", "okf_version": "0.2",
      "deprecated_on": null, "sunset_on": null, "superseded_by": null,
      "manifest": "v2/manifest.json", "entry": "v2/llms.txt",
      "endpoint_catalog_json": "v2/references/endpoint-catalog.json" }
  ]
}

When v3 ships it is appended as a second entry, latest becomes "v3", and the v2 entry gains status: "deprecated", a deprecated_on date, a sunset_on date and superseded_by: "v3". A client that stored latest can diff it and know a migration exists — from the manifest alone, without reading a changelog. Nothing under v2/ moves, and a deprecated bundle is never deleted.

StatusMeaningWhat an agent should do
betaPublished for early access; content may change without a major bundle bump.Use only if asked for it by name.
stableReady for production and actively maintained.The default. This is what latest points at.
deprecatedStill served and still correct, but superseded.Answer, and mention superseded_by and sunset_on.

Any LLM through an API — OpenRouter, Ollama, vLLM, Bedrock, Vertex…

No agent framework needed. Put the documents an agent would open into the prompt and ask the question. This is exactly how the open models were evaluated (Nemotron-3 120B: 51% → 98%; Ling-3.0 Flash: 19% → 100%). Note how the version is resolved in code, so the prompt can never see two versions at once.

# python — works with any OpenAI-compatible endpoint (OpenRouter, Ollama, vLLM, LM Studio …)
import json, os, urllib.request

REPO = "analytics-okf"                       # git clone https://github.com/sathishkumar-ks-8646/analytics-okf
# Resolve the version ONCE, in code. The prompt then physically cannot mix versions.
index   = json.load(open(f"{REPO}/manifest.json"))
entry   = next(v for v in index["versions"] if v["version"] == index["latest"])
BUNDLE  = f"{REPO}/{entry['path']}"          # -> analytics-okf/v2
print("using", entry["version"], "bundle", entry["bundle_version"])

def doc(p): return open(f"{BUNDLE}/{p.lstrip('/')}", encoding="utf-8").read()
def error_entry(code):
    s = doc("/foundations/error-codes.md"); i = s.find(f"## Error {code}\n"); return s[i:s.find("\n## Error ", i+5)]

question = "Share view 123 in workspace 456 with jane@example.com read-only, rows where Region='East'. Then explain error 7301."
context = "\n\n".join([
    f"===== {p} =====\n{doc(p)}" for p in [
        "/how-to-use-this-bundle.md",
        "/workflows/share-view-with-row-filter.md",
        "/domains/share-and-publish/sharing/share-views.md",
        "/foundations/filter-criteria-syntax.md"]] +
    [f"===== /foundations/error-codes.md (excerpt) =====\n{error_entry(7301)}"])

body = {"model": "nvidia/nemotron-3-super-120b-a12b:free", "temperature": 0.2, "messages": [
    {"role": "system", "content": f"Use ONLY the supplied bundle documents as the source of API facts. "
                                  f"They are Zoho Analytics REST API {entry['version']}. "
                                  f"Quote the document path for each fact."},
    {"role": "user", "content": context + "\n\n===== TASK =====\n" + question}]}
req = urllib.request.Request("https://openrouter.ai/api/v1/chat/completions", json.dumps(body).encode(),
      {"Authorization": "Bearer " + os.environ["OPENROUTER_API_KEY"], "Content-Type": "application/json"})
print(json.load(urllib.request.urlopen(req))["choices"][0]["message"]["content"])
# Ollama, one-liner: a local model with one endpoint document in context
ollama run llama3.1 "$(cat analytics-okf/v2/domains/share-and-publish/sharing/share-views.md)

Using only the document above: give the HTTP method, path, headers, CONFIG and scope to share view 123 read-only to jane@example.com."

Follow the bundle's own navigation rules (below): endpoint document for facts, workflow for multi-step jobs, request-conventions.md for encoding, the error-catalog entry for a failure. RAG pipelines and internal copilots (support, Zia-style assistants)

The bundle is pre-chunked: ~500 files per version, each one concept, each with typed YAML frontmatter. Index files, not fragments, and use the frontmatter as metadata filters. Version is the one filter you must not skip — once two versions are in the same index, similarity search will happily return both for the same query.

# python — index every version, with api_version as a hard metadata filter
import glob, json, yaml, re
from langchain_core.documents import Document

index = json.load(open("analytics-okf/manifest.json"))
docs = []
for entry in index["versions"]:                      # v2 today; v3, v4 … automatically
    root = f"analytics-okf/{entry['path']}"
    for path in glob.glob(f"{root}/**/*.md", recursive=True):
        text = open(path, encoding="utf-8").read()
        m = re.match(r"^---\n(.*?)\n---\n(.*)$", text, re.S)
        meta = yaml.safe_load(m.group(1)) if m else {}
        api = meta.get("api", {}) or {}
        docs.append(Document(page_content=m.group(2) if m else text, metadata={
            "api_version": entry["version"],         # ← filter on this, always
            "version_status": entry["status"],
            "path": path[len(root) + 1:], "type": meta.get("type"), "title": meta.get("title"),
            "operation_id": api.get("operation_id"), "method": api.get("method"), "http_path": api.get("path"),
            "scopes": ",".join(api.get("oauth_scopes", []) or []),
            "error_codes": ",".join(map(str, api.get("error_codes", []) or []))}))

# At query time — never leave api_version unset:
#   retriever.invoke(q, filter={"api_version": user_version or index["latest"]})
# retrieval tips: filter type=="API Endpoint" for how-to questions; look up error codes by
# anchor, not by similarity:  foundations/error-codes.md#error-7301 → deterministic answer.

For support assistants the two highest-value lookups are deterministic, not semantic: error-codes.md#error-<code> (meaning, status, fix, which operations raise it) and permission-matrix.md (scope + role per endpoint). Both must still be scoped to the customer's API version.

Build your own tool surface: bundle + one generic call

An MCP server hard-codes one tool per operation. The bundle lets you skip that: give the agent one generic HTTP tool and the bundle as knowledge, and it composes any of the 168 endpoints itself. This is what the live evaluation did (the "REST wrapper"), and it worked on the smallest model tested.

The pattern

One tool, all endpoints

The tool only adds what the agent must not know — the token and the org header. Method, path and CONFIG come from the bundle. Wrap it as an MCP server, a LangChain tool, or a function call and you have a full-API "personal MCP" that stays current every time the bundle is regenerated.

# minimal generic tool (python, OpenAI-style function schema)
import requests, os, json
def zoho_analytics_call(method: str, path: str, config: dict | None = None, files: dict | None = None):
    """Call the Zoho Analytics REST API. Take method, path, CONFIG shape and location from the OKF bundle."""
    url = "https://analyticsapi.zoho.com" + path
    h = {"Authorization": "Zoho-oauthtoken " + os.environ["ZA_TOKEN"], "ZANALYTICS-ORGID": os.environ["ZA_ORG"]}
    if files:   r = requests.request(method, url, headers=h, data={"CONFIG": json.dumps(config or {})}, files=files)   # multipart imports
    elif method == "GET": r = requests.get(url, headers=h, params={"CONFIG": json.dumps(config)} if config else None)
    else:       r = requests.request(method, url, headers=h, data={"CONFIG": json.dumps(config or {})})                 # form field CONFIG
    return {"status": r.status_code, "body": r.text[:4000]}
What the agent does with it

Reads, then calls once

Asked to "share table X read-only to Jane, rows where Region = East", an agent with the bundle opens workflows/share-view-with-row-filter.md → share-views.md, then calls:

zoho_analytics_call("POST", "/restapi/v2/workspaces/{ws}/share",
  {"viewIds": ["{view}"], "emailIds": ["jane@example.com"],
   "permissions": {"read": true},
   "criteria": "\"Region\"='East'"})          → 204
zoho_analytics_call("GET", "/restapi/v2/workspaces/{ws}/share/shareddetails",
  {"viewIds": ["{view}"]})                    → criteria stored, isInvalidCriteria:false

Without the bundle the same agents tried /shares/tables, emails, permission:"VIEW", filterCriteria:{…} — 8542, 8504, 8525 — and two of them shared without the filter first.

Guardrails

Keep the agent honest

Three lines that made the evaluated runs safe: "never guess a key name or path — if the bundle does not say, say so"; "verify with the read endpoint the playbook names before reporting success"; and for destructive steps, "state the criteria string before executing it". Pair with the smallest OAuth scopes the endpoint documents list — they are in every frontmatter.

Add a fourth once a second version exists: "the path prefix in the endpoint document and the one you call must come from the same bundle". A v3 path composed from a v2 document is a 404 at best and the wrong operation at worst.

The api.path carries its own version prefix (/restapi/v2/…), so a request composed from a bundle document is always self-consistent — another reason not to blend documents from two version directories.

The seven navigation rules

From how-to-use-this-bundle.md. Tell an agent to follow these — inside one resolved bundle — and it finds the right file in one or two hops.

FAQ

Should I link people to /tree/main/v2?

No, for two reasons. It is GitHub's HTML file browser, so a fetching agent gets page chrome instead of markdown — use raw.githubusercontent.com or a clone. And it pins silently: readers who wanted "the current API" are stuck on v2 after v3 ships. Link the repository root and let manifest.json resolve the version.

When v3 exists, will an agent use only v3 by default?

Only if you make it. Resolving latest gets it to v3; the rule "read nothing outside the resolved bundle, and never fall back to another version" is what keeps it there. Without that line a missing v3 document sends the agent to the v2 one, and the blended answer looks perfectly confident. In RAG, make api_version a hard filter, not a similarity outcome.

Why put every version in one repository?

One clone, one issue tracker, one CI run, and version selection becomes data (manifest.json) rather than tribal knowledge about which repo is current. Because each version is a self-contained directory that never moves, "same repository" costs nothing in isolation — the agent still reads exactly one bundle.

Do I need the whole bundle in context?

No. Agents open 3–6 files per task (5–21k tokens). For direct API calls, include the endpoint document, the workflow if multi-step, and the error entry if debugging — or let the model pick files from how-to-use-this-bundle.md plus the file list.

Which models does it work with?

Anything that reads text. Evaluated: Claude Opus, Sonnet, Haiku (agentic), Nemotron-3 Super 120B and Ling-3.0 Flash (direct calls). The smaller the model, the bigger the gain.

Is it a replacement for the MCP server or the SDKs?

No — it is what they, and any agent, read to make the right call. Tools execute; the bundle knows. Together they cover the whole API with one generic executor.

How current is it?

Generated from the API reference and OpenAPI specs; each version's manifest.json carries the bundle version and generated.at, and every concept carries generated.by and generated.at. Trust tier is currently unverified (faithful to the docs, not yet re-confirmed line by line against the live service); the share endpoints were verified live in the evaluation.

Does it expose customer data or internals?

No. Every fact comes from the public API reference and OpenAPI files; the validator refuses any provenance link pointing outside the bundle.

Where do I report a wrong fact?

Open an issue on the repository with the API version, the bundle version from <v>/manifest.json and the document path. Reviewers can add verified entries to concepts they confirm.
